# Waarom Mijn AIisajoke_v2 Development Harness Echt Lekker Werkt

Er zijn inmiddels genoeg AI coding demo's die vijf minuten indrukwekkend zijn en na een week onbruikbaar worden.

Precies dat wilde ik voorkomen met **AIisajoke_v2**.

Dus in plaats van één gigantische "autonome developer agent" te bouwen, heb ik er een **development harness** omheen gezet. Harness is hier eigenlijk een beter woord dan agent, want de echte waarde zit niet alleen in codegeneratie. De echte waarde zit in de rails eromheen:

- ik hou zelf controle over welke subscriptions ik betaal
- samenwerken blijft gewoon via GitHub lopen
- cronjobs verdelen het werk over de tijd in plaats van alles tegelijk te starten
- validatie gebeurt via vaste workflows voordat iets als klaar telt

Juist die combinatie maakt deze setup in de praktijk veel lekkerder dan de gemiddelde all-in-one AI tool.

## Het Doel Was Nooit "Maximale Autonomie"

De verleiding bij AI development is logisch: laat één tool gewoon alles end-to-end doen.

In de praktijk levert dat vaak een broos systeem op:

- één vendor wil prompting, execution, opslag en deploy allemaal tegelijk bezitten
- je kosten verdwijnen in subscriptions waar je weinig grip op hebt
- failures zitten verstopt in één ondoorzichtige interface
- samenwerken wordt lastiger omdat de echte state buiten GitHub leeft

Ik wilde juist het tegenovergestelde.

Ik wilde een setup waarin AI hard meewerkt, maar de workflow nog steeds voelt als een professionele softwarestraat.

## Ik Hou Zelf Regie Op Mijn Eigen Subscription Stack

Eén van de fijnste eigenschappen van deze harness is dat ik **niet** alles hoef uit te leveren aan één platform.

Ik kan per laag kiezen wat ik inzet:

- GitHub voor issues, PR's, reviews en samenwerking
- Codex/OpenClaw voor agent runtime en orchestration
- mijn eigen cronjobs voor timing en automatisering
- GitHub Actions en project-workflows voor validatie

Dat is belangrijker dan het op het eerste gezicht lijkt.

Als een tool morgen zijn pricing, rate limits of productrichting verandert, hoef ik niet mijn complete proces opnieuw uit te vinden. Ik kan één laag aanpassen, een script vervangen of verschuiven waar ik geld uitgeef. Dat is een veel gezondere positie dan je volledige development flow vastzetten in één abonnement.

Anders gezegd: **AI-acceleratie is mooi, maar eigenaarschap over je operating model is nog waardevoller**.

## GitHub Blijft Het Gedeelde Punt Van Waarheid

Nog een reden waarom deze setup goed werkt: het teamwerk blijft plaatsvinden op een plek die developers al begrijpen, namelijk **GitHub**.

De harness leest triggers uit issues en comments, opent branches en PR's, en rapporteert terug in dezelfde thread. Daardoor blijft:

- het issue het planningsobject
- de PR het wijzigingsobject
- de comment thread de discussielaag
- labels en workflows de operationele state

Dat is cruciaal zodra je met meer dan één persoon werkt.

Zonder die keuze wordt AI-werk snel persoonlijk en onzichtbaar. Eén iemand weet dan wat de agent gedaan heeft omdat die de terminal heeft gezien, terwijl de rest van het team alleen ergens een mysterieuze branch ziet opduiken. Dat schaalt niet.

Door GitHub centraal te houden blijft de flow leesbaar voor mensen. AI mag snel zijn, maar mensen moeten nog steeds kunnen reviewen, ingrijpen en beslissen.

## Crons Verdelen De Belasting Over De Tijd

Dit is misschien wel het meest onderschatte deel van de setup.

Ik wil niet dat elk issue, elke retry, elke repair en elke monitoractie exact op hetzelfde moment vuurt. Dat geeft ruis, onnodige concurrentie om resources en een veel lastiger debugverhaal.

Daarom gebruikt de harness cron-gebaseerde pacing:

- één cron doet intake
- een andere cron doet monitoring
- follow-up acties zoals retries of repairpogingen gebeuren in gecontroleerde intervallen

Daardoor krijgt het systeem lucht.

In plaats van een chaotisch burst-model krijg ik een **pipeline die over de tijd verdeeld is**. Nieuw werk wordt gestaag opgepakt. Lopend werk wordt later opnieuw gecontroleerd. Failing werk krijgt opnieuw een kans zonder dat het hele systeem verandert in een stampede.

Dat is niet alleen operationeel fijner, het werkt ook beter voor teamwork:

- minder botsingen
- makkelijker prioriteren
- duidelijkere logs
- voorspelbaarder gebruik van infrastructuur

## Validatie Leeft In Workflows, Niet In Agent-zelfvertrouwen

Dit is misschien het belangrijkste architectuurpunt.

Ik vertrouw "de agent denkt dat het klaar is" niet als releasesignaal.

De harness wordt pas echt bruikbaar zodra validatie buiten de agent wordt geplaatst en in herhaalbare checks landt. Dat betekent dat de kwaliteitslat in workflows zit, niet in de stemming van het model.

Dus de flow draait bewust om dingen als:

- branch- en PR-creatie
- CI-checks
- workflowresultaten
- expliciete reviewmomenten
- monitoring na de run

Die keuze verandert eigenlijk alles.

Want daardoor hoeft de agent niet magisch betrouwbaar te zijn. Hij hoeft alleen nuttig te zijn binnen een systeem met harde randen. Hij mag code schrijven, tests aanpassen, failures oppakken en PR's openen, terwijl de omliggende workflows bepalen of de wijziging echt gezond is.

Dat is voor mij precies het verschil tussen een leuke demo en een echte development harness.

## Waarom Dit Voor Mij Een "Lekkere Setup" Is

Een goede AI development setup moet voor mij rustig, modulair en eerlijk aanvoelen.

Deze doet dat.

Het voelt goed omdat:

- ik niet vastzit aan één subscription-afhankelijkheid
- samenwerken gewoon in GitHub gebeurt, waar het team al werkt
- cron scheduling voorkomt dat alles tegelijk gebeurt
- validatie expliciet en herhaalbaar is
- het systeem onderdeel voor onderdeel beter kan worden zonder complete rewrite

Dat laatste punt is groot.

Ik hoef niet eerst te stoppen en een enorm AI-platform vanaf nul te bouwen. Ik kan gewoon één laag tegelijk verbeteren: betere prompts, nettere run artifacts, slimmere retries, duidelijkere monitor comments, strengere validatieregels. De harness groeit door zonder zijn vorm te verliezen.

## Mijn Praktische Regel Voor AI Development

Als je AI wilt laten meebouwen aan echte software, zou ik niet beginnen met "hoe maak ik dit autonomer?"

Ik zou beginnen met:

1. Hoe hou ik controle over kosten en subscriptions?
2. Hoe maak ik het werk zichtbaar voor het team in GitHub?
3. Hoe spreid ik de belasting zodat het systeem stabiel blijft?
4. Hoe valideer ik veranderingen via workflows in plaats van op gevoel?

Precies daarom werkt deze AIisajoke_v2 harness voor mij.

Hij is niet flitsend op de verkeerde plekken. Hij is sterk op de saaie plekken.

En dat is meestal precies wat je wilt als je iets bouwt dat je over een maand nog steeds wilt gebruiken.
